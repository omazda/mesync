# Локальный Telegram Bot API сервер — снятие лимита на размер файлов

Облачный `api.telegram.org` жёстко ограничивает кросс-мессенджерный перенос медиа:
**скачивание ≤ 20 МБ** (`getFile`) и **multipart-загрузка ≤ 50 МБ** (10 МБ для фото).
Это предел облачного Bot API, не нашего кода (сверено с
`docs/telegram/markdown/04-api-reference.md`, строки 1578 и 3074).

Свой Bot API сервер **в режиме `--local`** снимает это (там же, раздел «Using a Local
Bot API Server»; подтверждено исходниками `telegram-bot-api` — лимиты сняты именно под
флагом `--local`, а не самим фактом self-hosting):

- **скачивание файлов без ограничения размера;**
- **загрузка файлов до 2000 МБ.**

После перехода кросс-мессенджер MAX↔TG ограничен **только трафиком**:
TG-сторона до 2000 МБ (предел загрузки в Telegram), MAX-сторона до 4 ГБ (предел MAX).
Внутри одного мессенджера (MAX→MAX, TG→TG) лимита по размеру нет и сейчас — там
переиспользуется `token`/`file_id` на стороне платформы, файл не перекачивается.

> Переводим на локальный сервер **только Telegram-сторону**. MAX не трогаем — у MAX
> свой API с нативным лимитом 4 ГБ.

## Как `--local` влияет на код (важно)

В режиме `--local` метод `getFile` возвращает в `file_path` **абсолютный путь файла на
диске сервера** (например `/var/lib/telegram-bot-api/<bot_id>/documents/file_5.jpg`), а не
относительный HTTP-путь. Поэтому:

- рабочая папка сервера примонтирована на хост **по тому же пути** (`docker-compose.yml`,
  том `/var/lib/telegram-bot-api:/var/lib/telegram-bot-api`);
- код бота (`src/telegram_sync/client.py`, `download_file`/`download_file_bytes`) определяет
  абсолютный путь и **читает файл прямо с диска**, без перекачки по HTTP. На облаке (путь
  относительный) поведение прежнее — качаем по HTTP. Никаких ручных переключений в коде нет.
- **Docker-права:** `compose.telegram-api.yaml` монтирует read-only только каталог текущего
  бота по тому же абсолютному пути и добавляет непривилегированному `mesync-app` (`uid 10001`)
  файловую группу Bot API (`gid 101`). Если образ Bot API использует другой host-путь или gid,
  задайте `TELEGRAM_API_DATA_DIR` и `TELEGRAM_API_FILE_GID` в корневом `.env` MeSync.
  Compose healthcheck отдельно проверяет чтение/обход этого каталога и помечает приложение
  unhealthy при ошибочном mount или gid. Внутри клиента этот каталог также является жёсткой
  границей: абсолютный `file_path` вне него и symlink-выход отклоняются.

## Что нужно от владельца (один раз)

`api_id` и `api_hash` приложения — их выдаёт **только личный аккаунт Telegram**:

1. Открыть <https://my.telegram.org> → войти своим номером.
2. **API development tools** → создать приложение (любое название/платформа).
3. Скопировать **api_id** (число) и **api_hash** (строка).

Это учётные данные *приложения*, не бота; токен бота при этом не нужен и не передаётся.

## Запуск сервера

```bash
cd deploy/telegram-bot-api
cp .env.example .env
# впишите в .env свои TELEGRAM_API_ID и TELEGRAM_API_HASH
docker compose up -d
docker compose logs -f --tail=30        # дождаться запуска без ошибок api_id/api_hash
```

Сервер слушает `127.0.0.1:8081` (доступен только хосту, где работает `mesync-app`).

```bash
nc -z 127.0.0.1 8081 && echo "порт жив"      # быстрая проверка
```

## Переключение бота на локальный сервер

> Токен бота можно использовать **только на одном** Bot API сервере. Перед запуском на
> локальном надо **выйти из облака** (`logOut`). После `logOut` вернуться в облако нельзя
> **10 минут** (docs, строка 3150). Подставьте реальный `<TG_TOKEN>` (из `.env` проекта,
> `TELEGRAM_BOT_TOKEN`).

```bash
# 1. Остановить бота, чтобы не конфликтовал getUpdates во время переключения
systemctl stop mesync-app

# 2. Выйти из облачного Bot API (ждём {"ok":true,"result":true})
curl -sX POST "https://api.telegram.org/bot<TG_TOKEN>/logOut"

# 3. В корневом .env проекта (/root/sync-bot/.env) выставить:
#      TELEGRAM_API_BASE=http://127.0.0.1:8081
#      MESYNC_TG_UPLOAD_MAX_BYTES=2097152000     # 2000 МБ — потолок загрузки MAX→TG / RAM TG→MAX
#      MAX_DOWNLOAD_BYTES=2097152000             # снять лимит скачивания TG→MAX/архива
#    (значения подхватятся при старте процесса)

# 4. Запустить бота — теперь он ходит на локальный сервер
systemctl start mesync-app
journalctl -u mesync-app -n 40 --no-pager    # убедиться: getMe ок, поллеры поднялись
```

Проверка вживую: отправить в источник файл крупнее 50 МБ и убедиться, что он дошёл в
целевой мессенджер (а не «текст + ссылка»).

## Откат на облако

```bash
systemctl stop mesync-app
curl -sX POST "http://127.0.0.1:8081/bot<TG_TOKEN>/logOut"   # выйти из локального сервера
# В /root/sync-bot/.env вернуть TELEGRAM_API_BASE на https://api.telegram.org (или убрать
# строку) и вернуть прежние лимиты (или убрать MESYNC_TG_UPLOAD_MAX_BYTES/MAX_DOWNLOAD_BYTES).
systemctl start mesync-app        # если облако ещё держит 10-мин паузу после logOut — подождать
docker compose -f deploy/telegram-bot-api/docker-compose.yml down
```

## Нюансы

- **file_id привязаны к серверу.** ID, выданные облаком, на локальном сервере недействительны
  (и наоборот). На пересылку это не влияет: бот и принимает, и отправляет через ОДИН сервер,
  а file_id для TG→TG берёт из живого входящего апдейта — не из старого кэша.
- **Память.** Перенос идёт через RAM (читаем байты → загружаем). Файл на 2 ГБ — это ~2 ГБ
  пикового RAM на сообщение; потолок задаёт `MESYNC_TG_UPLOAD_MAX_BYTES` (оба направления).
  Для типового медиа (<100 МБ) несущественно; полностью убрать RAM-давление можно потоковой
  передачей через диск (`download_file` → загрузка из файла) — отдельная доработка кода.
- **Диск.** В режиме `--local` сервер складывает скачанные/загружаемые файлы в рабочую папку
  (`/var/lib/telegram-bot-api`) и не всегда чистит их сам — следить за местом
  (`du -sh /var/lib/telegram-bot-api`, при необходимости периодически удалять старое).
- **Сеть.** Сервер опубликован только на `127.0.0.1:8081` — снаружи недоступен. Левую часть
  маппинга порта (`127.0.0.1`) не менять: без `--local`-аутентификации доступ к серверу = доступ
  к боту по токену.
